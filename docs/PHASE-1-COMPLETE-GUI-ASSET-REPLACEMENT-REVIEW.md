### Decision-specific findings

- **Rows 1–5, 7, 9–10, 12–21, 23 — HOLD (19 assets).** These are the four brand SVGs, fourteen non-Lucide icon SVGs, and one ICO. The proposal report describes the 18 SVGs as fresh drawings for this task, but there is no itemized creator/rights-holder identity, explicit redistribution grant, or notice/license record for them in the proposal tree. The ICO is a derivative export of the proposed app-icon per the report; its source/artwork rights therefore need the same documented chain. Do not infer historical ownership or rights in the original artwork from filenames, commit authorship, duplication, or the proposal report. The visible proposal drawings render and have internally coherent styling, but this review cannot clear redistribution or integration rights without those records. The wordmark/sidebar use live SVG `<text>` with system font fallbacks, so platform appearance may differ; validate against supported Windows/Qt layouts and themes after rights are documented.
- **Row 6 — NEEDS CORRECTION (`check.svg`).** The staged file is the reported pinned upstream SVG and its path geometry matches the original. However, live `icons.py` replaces the literal `CURRENT_COLOR` token only; this proposal uses `stroke="currentColor"`. In isolated Qt rendering it therefore renders black rather than the requested theme color. A corrected asset/contract and theme-render verification are needed. Also settle the final applicable Lucide/Feather notice scope before integration.
- **Row 8 — NEEDS CORRECTION (`download.svg`).** Same `currentColor`/`CURRENT_COLOR` mismatch and resulting black icon. Source pin and geometry evidence are in the proposal report; verify the licensing/notice decision before any integration.
- **Row 11 — NEEDS CORRECTION (`folder-open.svg`).** Same color-token mismatch. In addition, the staged basename uses a hyphen (`folder-open.svg`) while the application requests `icons/folder_open.svg`; simply copying the proposal into the asset directory would leave the runtime lookup unresolved. A deliberate destination mapping/rename or approved reference change is needed; this review authorizes neither. Resolve notice scope as well.
- **Row 22 — NEEDS CORRECTION (`x.svg`).** Same `currentColor`/`CURRENT_COLOR` mismatch and black rendering in the current runtime loader. Correct the color contract and verify the exact applicable notices before integration.

## 3. Inventory, mapping and GUI-reference resolution

All four Lucide files are 24×24. Both ICOs contain the same seven declared sizes (16, 24, 32, 48, 64, 128, 256). No asset is missing from the isolated proposal directory; no dimensions/formats differ from their mapped targets.
- All 19 proposals under `original-proposals` preserve the target-relative filename. The four Lucide mappings preserve the intended target names in their attribution table, but the staged `folder-open.svg` file must be installed under `folder_open.svg` to satisfy current lookup behavior. The three other Lucide basenames match.
- Runtime `icon_svg()` reads `assets/icons/{name}.svg`; brand loaders read the `logsentinel-mark.svg`, `logsentinel-logo.svg`, and `logsentinel-sidebar.svg` names. `tests/test_gui_themes.py` requires all four brand filenames and 13 named icon files. Both GUI packaging recipes collect SVG and ICO assets from the live asset root. Therefore replacement proposals must be integrated at the target paths, not left in `licenses/...`, and preserve these names/viewBoxes. The unintegrated proposal tree does not itself resolve any current GUI reference.
- Proposed brand and original-design icon token names are compatible with the existing replacement routines by inspection (`CURRENT_*` tokens used by brand substitution; `CURRENT_COLOR` used by icon-color substitution). The four raw Lucide proposals use standard SVG `currentColor`, which this app’s current literal-token replacement does not rewrite; isolated Qt render verification showed black output. This is a real integration defect, not a hash/geometry issue.
- `logsentinel-appicon.svg` and `logsentinel-mark.svg` are byte-identical in both original and proposed sets (SHA-256s repeat exactly). This is an intentional duplicate mapping that satisfies the test’s requirement for both paths and is not an accidental duplicate/missing asset. It should remain understood as duplicated content, not represented as two independent designs.

## 4. SVG geometry, visual consistency and accessibility

- All 22 proposed SVGs parse as XML, have the expected SVG root/viewBox and render via Qt `QSvgRenderer` after applying the documented theme-token substitution. No scripts, `foreignObject`, embedded image, iframe, or remote asset references were found in these SVGs. All render with non-empty pixels at their declared default dimensions.
- The four raw Lucide proposed path-data multisets equal their mapped original path-data multisets. This corroborates the reports’ geometric comparison for the candidates; it does not independently establish historical origin of the originals. `download` has a different path element order. The replacement files are upstream-style width 2 while existing art uses width 1.8; 2 is consistent across the staged design proposals but visibly changes stroke weight relative to the live originals. Check at actual widget sizes during any later correction/integration review.
- The 19 original-design proposals share 24×24 round-cap/round-join, nominal 2px icon strokes. In the dark contact sheet the icons are visually distinguishable, legible as conventional controls/navigation symbols, and generally stylistically coherent. Brand mark/app-icon/wordmarks share the shield/log-lines and gradient-tile treatment. This is a material identity change from the existing eye-motif brand fallbacks/artwork, not a faithful visual continuation; owner/product approval would be needed in addition to technical and rights review. No missing geometry or obvious malformed/distorted drawing was found in the checked dark preview. This is a visual review, not a uniqueness, trademark, or legal assessment.
- The contact sheet `licenses/third-party/asset-remediation/original-proposals/contact-sheet.html` embeds all 18 SVG proposals and displays the ICO’s 256×256 frame. It rendered at 1200px and 390px with no browser console messages; mobile layout remains scrollable, and the visible labels identify assets. This review did not run a screen-reader or full GUI accessibility audit. Contact sheet’s ICO `<img>` has alt text; individual inline SVGs are captioned with their filenames but are not given explicit ARIA labels.
- No light-theme preview, Windows font substitution matrix, high-DPI widget capture, or application integration render was performed. The report’s wordmarks use live text and system-font fallback, not outlines or embedded fonts; appearance depends on installed fonts.

No proposal is approved for copying into the live asset directory by this report.

The reviewed upstream license files and replacement report are evidence for the staged candidates, not proof of historical origin or ownership of the 23 originals. No legal opinion, uniqueness search, trademark clearance, creator interview, light-theme acceptance, screen-reader audit, build/test validation, Windows shell integration test, or release authorization was performed. Hash agreement proves byte identity only.
