## 2. Per-finding register

### PUB-01 — `.gitignore` coverage and concrete staging exposure

- **Exact path(s):** `.gitignore` (lines 6–21); `.venv-build/`, `.venv-build-gui/`; `test-results.txt`; `test-results-local.txt`; `release/` and the files below it; root report/audit artifacts.
- **Current status:** `.gitignore` is tracked and unchanged in this task. Its venv entries are literal `.venv/`, `venv/`, and `env/` (lines 12–15), not a wildcard for `.venv-build*`. The two current build venv directories each contain their own generated `.gitignore` with `*`; Git currently reports their contents ignored through those nested files. `git check-ignore --no-index` confirms the root directory names themselves do not match the repository `.gitignore`. `test-results.txt`, `test-results-local.txt`, and all observed `release/` files are untracked and **not ignored**. The current exact report names `report.json`, `report.txt`, `report-explicit.json`, and `audit-*` are ignored; alternative report names are not covered by those exact entries. Root `build/`, `dist/`, and `*.egg-info/` are covered.
- **Concrete files/directories exposed:**
  - `.venv-build/` and `.venv-build-gui/` contain installed Python/build dependencies. Current contents are ignored by their nested generated ignore files, so a normal broad add does not currently list them. If those nested files are removed/replaced, or a force-add is used, large installed environments and third-party files could be staged. They are about 4,319 and 8,239 files respectively in this snapshot.
  - `test-results.txt` (219,812 bytes) and `test-results-local.txt` (104,586 bytes) are UTF-16 PowerShell-captured test output, not canonical test artifacts. One contains an older **332-test run with 49 failures and 1 error**; the other ends with **416 tests, OK (skipped=2)**. Their beginnings include PowerShell `NativeCommandError` wrappers. They are not covered by `.gitignore`.
  - `release/LogSentinel-Windows-v0.1.0/` contains untracked `LogSentinel.exe` (9,922,891 bytes), `LICENSE`, `README.md`, `SHA256SUMS.txt`, and `from pyzbar import pyzbar.py`; sibling `release/LogSentinel-Windows-v0.1.0.zip` is 9,733,515 bytes. The directory and files are not ignored. The ZIP contains four members (`LICENSE`, `LogSentinel.exe`, `README.md`, `SHA256SUMS.txt`) and does **not** contain the anomalous `.py` file.
  - Generated reports include `report.json`, `report.txt`, and `report-explicit.json` (these exact names are ignored), plus the root `audit-*` logs/configs/reports (also ignored). Other generated names may not match the current rules.
- **Risk if published:** a careless `git add .` / `git add -A` can add the two test-result logs and the whole `release/` directory, including a Windows executable/ZIP that is explicitly outside this source-only request and still on legal HOLD. Test logs can expose failed assertion values, local paths, environment details, and stale/conflicting results. Venv contents are a conditional risk if their nested ignore files change or force-add is used; their current ordinary-add risk is lower than the earlier review implied.
- **Recommended correction (not applied):** in a separately approved change, consider a robust root ignore pattern for build venvs, test-result files, and the local `release/` output if those paths are never maintained source. Regardless of ignore changes, stage a reviewed allowlist and inspect `git status --short --untracked-files=all`, staged diff, and staged file names/types. Keep report/audit outputs excluded unless each is intentionally converted to a reviewed synthetic fixture.
- **Safe and reversible?:** adding ignore patterns is normally safe and reversible, but patterns can hide future intentional files; choose scoped patterns and validate `git check-ignore` behavior. Excluding these local outputs from a future staging set is safe and reversible. Do not delete existing artifacts as part of that correction.

### PUB-02 — Unrelated `pyzbar` / OpenCV Python file

- **Exact path:** `release/LogSentinel-Windows-v0.1.0/from pyzbar import pyzbar.py`.
- **Current status:** untracked in the working tree, 583 bytes, SHA-256 `3b61a54ceb89d0635ae42e36e9d1c00facedd7de6db08e2a3acbbdf237202279`. It is absent from both `main` and `origin/main` trees. It appears in local `refs/t3/orchestration-v2/checkpoints/...` history: the path was added in checkpoint commit `8e183c2` (and repeated checkpoint snapshots), alongside the original repository/release snapshot. Those refs are not ancestors of `main` or `origin/main`; `main` has no `release/` path. Do not treat local checkpoint history as evidence of an upstream project origin. The public Git remote/refspec and whether anyone intends to publish checkpoint refs were not inspected.
- **Observed contents/purpose:** the file imports `pyzbar` and `cv2`, assembles barcode fields named `Dob`, `Doh`, `Doe`, `DaN`, `DaS`, `DaC`, and related keys, labels the data “Sample Texas DL data,” and supplies values resembling a date of birth, Texas address, name, and driver-license number. It then reads the placeholder `path/to/background.png` and attempts barcode decoding. No LogSentinel source, tests, docs, packaging metadata, or the release ZIP references this snippet or those dependencies. The file appears to be a standalone driver-license/barcode experiment unrelated to LogSentinel; its actual author, source, license, and whether the PII-shaped values are fabricated are **not established**.
- **Risk if published:** unrelated code and unexplained dependencies confuse the project boundary; the sample values could be mistaken for real personal data or be copied from an external example; its license/provenance is unknown. If publishing local checkpoint refs or mirroring all refs, the path may be included in Git history even when absent from `main`.
- **Recommended correction (not applied):** exclude the entire local `release/` directory from any source-only staging allowlist. Do not incorporate this file into LogSentinel source. If future provenance investigation is desired, identify its origin and confirm whether the values are fabricated before reuse. For publication, explicitly verify the push refspec and proposed refs; publishing only reviewed `main` history does not include the observed checkpoint-only path, whereas publishing/mirroring those checkpoint refs may.
- **Safe and reversible?:** excluding the file from a future allowlist is safe and reversible and leaves the local artifact intact. Deleting it or rewriting checkpoint history is not authorized here and is not necessary to keep it out of a `main`-only source publication. History rewriting is potentially destructive and should not be treated as a routine correction.
